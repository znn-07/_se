# 附錄 B：與 AI 對話探索過程

> 說明：以下為本書撰寫期間與 AI 對話的**整理版**，非逐字謄錄。保留的是「我問了什麼、哪裡想錯、後來怎麼改」——因為錯誤的修正過程比正確答案更有學習價值。文中連結指向整章檔案，節次請在檔案內搜尋標題。

---

## 對話 1：先問一個笨問題

**我：** ReAct 和 Function Calling 到底差在哪？我感覺都在讓模型叫工具。

**AI 回覆摘要：** 兩者不在同一個層次。ReAct 是「Thought → Action → Observation」的迴圈結構；Function Calling 是模型表達「想呼叫某函式」的 API 協定。你可以用 regex 做 ReAct，也可以只做一次 Function Calling 而完全沒有迴圈。

**我當下的反應：** 以為 AI 在玩文字遊戲。

**之後的修正：** 寫完第五章才真的懂——`parse_action()` 是 ReAct 的一部分，`SYSTEM_PROMPT` 裡的工具清單是協定的一部分。一個管「何時再來一輪」，一個管「這一輪長什麼樣子」。→ 寫進 [第二章 2.1](02-react-architecture.md) 與 [第三章 3.2](03-function-calling.md)。

---

## 對話 2：Observation 到底是誰寫的？

**我：** 模型不是會自己寫 Observation 嗎？範例裡看起來都是模型輸出的。

**AI 回覆摘要：** 在標準 ReAct 裡，Observation 由執行工具的程式產生。模型如果自己寫 Observation，就是幻覺被「合法化」——它先假裝查到資料，再根據假資料推理。

**我追問：** 所以 Prompt 裡要叫它不要寫？

**AI 回覆摘要：** 可以寫，但不可靠。真正的保證是「程式把工具結果放回 messages」，並在解析時忽略模型自己生成的 Observation 欄位。

**我學到的事：** 安全邊界不在Prompt，在程式。→ [第二章 2.2](02-react-architecture.md)、[第五章 5.2](05-minimal-react-agent.md)。

---

## 對話 3：Prompt 裡寫「不要亂來」有用嗎？

**我：** 我在 System Prompt 寫了「絕對不要呼叫刪除工具」，這樣夠安全嗎？

**AI 回覆摘要：** 這是「建議」不是「保證」。模型可能忽略、也可能被間接注入的文件覆寫。要保證，就要在工具註冊表做 allowlist，並把不可逆動作放到人工覆核節點。

**我追問：** 那 Prompt 完全沒用嗎？

**AI 回覆摘要：** 有用，但用在「行為偏好」，不是「安全保證」。安全要靠流程。

**我學到的事：** 分清楚「影響模型」與「約束系統」。→ [第三章 3.3](03-function-calling.md)、[第七章 7.2](07-conclusion.md)。

---

## 對話 4：context window 是記憶嗎？

**我：** 模型有 128K context，是不是就等於有 128K 的記憶？

**AI 回覆摘要：** 比較好的說法是「工作記憶」或「桌面」。沒放上桌面的資料模型不知道；放太多又會稀釋注意力。而且每次呼叫都要重新付費送出這些 token。

**我追問：** 那長期記憶怎麼做？

**AI 回覆摘要：** 用 RAG：切塊、向量化、檢索、rerank，需要的時候才放進 Prompt。所以「記憶」其實是檢索策略。

**我學到的事：** 短期靠 messages 管理，長期靠檢索。→ [第一章 1.1](01-stateless-llm-api.md)、[第四章 4.4](04-architectural-pillars.md)。

---

## 對話 5：RAG 還是微調？

**我：** 想讓模型懂我們公司的內部規則，該 RAG 還是微調？

**AI 回覆摘要：** 先問「規則會不會變」。會變 → RAG（改文件即可）；不會變且要改變行為風格 → 微調。大多數企業知識管理屬於前者。

**我追問：** 所以微調比較不重要？

**AI 回覆摘要：** 不是不重要，是解決的問題不同。微調改的是「怎麼回答」，RAG 改的是「看得到什麼資料」。而 Agent 的安全與流程問題，兩者都解決不了。

**我學到的事：** 選型要先分類問題。→ [第四章 4.4](04-architectural-pillars.md)。

---

## 對話 6：我的 regex 一直解析失敗，該不該換框架？

**我：** 模型有時候在 `Action:` 後面補一句解釋，我的 regex 就抓錯了。是不是該直接用 LangGraph？

**AI 回覆摘要：** 先別急。失敗原因是格式約束不夠，不是流程不夠。三個層級的解法：加 few-shot 範例 → 改用 JSON 輸出 → 改用原生 Function Calling。框架解決的是狀態與重試，不是格式。

**我追問：** 那什麼時候才真的需要框架？

**AI 回覆摘要：** 當你需要 checkpoint、分支並行、人工節點、trace/replay 時。單純的線性迴圈不需要。

**我學到的事：** 「換工具」之前先診斷問題層級。→ [第二章 2.3](02-react-architecture.md)、[第六章 6.1](06-frameworks-and-multi-agent.md)。

---

## 對話 7：多 Agent 是不是比較厲害？

**我：** 我打算做三個 agent：一個查資料、一個寫答案、一個檢查。這樣品質會比較好吧？

**AI 回覆摘要：** 可能，但你先付了三倍的呼叫成本，還多了幻覺互相傳播的風險。檢查者如果沒有客觀依據（例如測試、規則），它只是另一個會幻覺的模型。

**我追問：** 那 Evaluator-Optimizer 為什麼又被推薦？

**AI 回覆摘要：** 因為它通常搭配客觀訊號——程式設計場景是測試與編譯器。有客觀 Observation 的迴圈才可靠。

**我學到的事：** 先找可靠的 Observation，再決定要不要多 agent。→ [第六章 6.3](06-frameworks-and-multi-agent.md)、[第七章 7.1](07-conclusion.md)。

---

## 對話 8：LangGraph、CrewAI、AutoGen 怎麼選？

**我：** 我要寫一本給決策者看的書，框架比較該怎麼寫才不會過時？

**AI 回覆摘要：** 不要比 API 細節，比心智模型：LangGraph 是狀態機、CrewAI 是角色任務、AutoGen 是 Agent 對話。加上「選型前查官方文件」的提醒。

**我追問：** 決策者真正該關心什麼？

**AI 回覆摘要：** 中斷恢復、人機關卡、可觀測性、責任邊界。不是「支援多少工具」。

**我學到的事：** 寫技術文件時，寫「設計哲學」比寫「功能清單」長壽。→ [第六章 6.1–6.2](06-frameworks-and-multi-agent.md)。

---

## 對話 9：上線前最小要有哪些防護？

**我：** 如果只能做三件事，我該做哪三件？

**AI 回覆摘要：** (1) 工具 allowlist + 參數驗證；(2) 不可逆動作的人工覆核；(3) 完整 trace。對多輪、高風險 Agent 而言，沒有 trace 就沒有 Eval，也無法事後追責。

**我追問：** 稽核紀錄要記什麼？

**AI 回覆摘要：** who / what / when / result，加上 agent 的 Thought 與 Action。但要把 API key、連線字串等機敏資料過濾掉。

**我學到的事：** 安全是可分優先順序的工程，不是一整套買來的產品。→ [第三章 3.3](03-function-calling.md)、[第七章 7.2](07-conclusion.md)。

---

## 對話 10：幫我檢查讀者會在哪裡卡住

**我：** 這本書對完全沒寫過 Agent 的人，哪一段最容易誤解？

**AI 回覆摘要：** 三個高風險點：(1) 把 ReAct 當成 Function Calling；(2) 以為 Observation 是模型寫的；(3) 以為 context window 等於記憶。建議在各章重複出現「程式持有歷史」這句話，並在第五章用 `--mock` 把流程隔離出來讓讀者觀察。

**我做了什麼：** 回頭修改第一章 1.3、第二章 2.2 與第五章 5.2，統一用「桌面」比喻，並強調 Observation 的產生者。

**我學到的事：** 讀者測試不是「問讀者滿意嗎」，而是問「你會怎麼回答這個問題」。→ [第五章 5.4](05-minimal-react-agent.md)。

---

## 對話 11：這本書該怎麼收尾？

**我：** 第七章要怎麼寫才不像制式結語？

**AI 回覆摘要：** 寫你「原本以為的三件錯事」，以及這本書還沒做到的地方。誠實的侷限比空洞的展望更有價值。

**我做了什麼：** 寫成 7.3，列出 ReAct/Function Calling、RAG/記憶、多 Agent 三個誤解，並承認沒有做框架對照與 red-team 測試。
